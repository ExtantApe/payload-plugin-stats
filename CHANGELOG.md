# Changelog

## Unreleased

- **First version.** A Payload 3 plugin that counts users and shows the counts to admins. Totals; new accounts yesterday, in the last 7 days and in the last 30 days (whole UTC days); counts by each configured select, radio or relationship field, as a high-level table (any, none, roll-ups) and a row per value, including `hasMany` fields and fields inside arrays; and count bands, users with more than N documents in another collection.
- **Aggregate only.** Every read of the users collection is a count. Count bands are one grouped count inside MongoDB that returns a single row of totals. No response holds a name, an email or an ID.
- **Small-group hiding.** A count under `minimum` (default 5) shows as "fewer than 5". Larger counts show as "hidden" when they would let a reader work out a small one by subtracting from a total, a sibling row, a roll-up or the next step of a ladder. With too few users for that to be enough, every number shows as "hidden".
- **Admins only.** A dashboard card, an admin view and `GET /api/stats`. `access` is a config function and must answer exactly `true`. The default is the users collection's `access.admin`, and the plugin refuses to start when there is neither.
- **CI.** Typecheck, tests against a MongoDB service container, and build, on Node 22.

Tested: 72 tests against a real Payload 3.92.1 and a real MongoDB 8 in a throwaway container. Counts for every table on made-up data (40 accounts), including an account with two roles counted in both, the same value in two array rows counted once, deleted owners left out of bands, and UTC day edges. Hiding: each rule on its own, the expected hidden cells on the made-up site, and a separate brute-force reader that tries every possible filling of the hidden cells on over 1,000 random reports and finds no small count it can narrow. Refusals at the endpoint, the card and the view for logged-out requests, a user with no role, three non-admin roles and an admin-flagged user from another auth collection; custom access answers other than `true`; 21 start-up refusals for bad options. No name, email or ID in the JSON, the card or the view. 9 mutation checks (for example: no complementary suppression, a truthy access answer accepted, the 403 removed) each fail at least one test.
Not tested: the card and the view in a browser inside a running Payload admin (they are rendered to HTML in tests, and the view's page frame from `@payloadcms/next` is typechecked only); the import map step; Postgres and SQLite; Node 22 locally (CI runs it); a site with real data.
