# Changelog

## 0.1.0 (2026-11-25)

- **First version.** A Payload 3 plugin that counts users and shows the counts to the people the site allows. Totals; new accounts yesterday, in the last 7 days and in the last 30 days (whole UTC days); counts by each configured select, radio or relationship field, as a high-level table (any, none, roll-ups) and a row per value, including `hasMany` fields and fields inside arrays; and count bands, users with more than N documents in another collection.
- **Aggregate only.** Every read of the users collection is a count. Count bands are one grouped count inside MongoDB that returns a single row of totals. No response holds a name, an email or an ID.
- **Small-group hiding, by structure.** No count from 1 to 4 shows (default minimum 5). What is hidden with it is fixed by the layout of the report and never by the sizes of the numbers: a field's rows and roll-ups are hidden together, a field's "any" and "none" are hidden together with them, and a list of steps (new-account windows, count bands) is hidden from the first small step down. A hidden count says nothing about its size. A zero in a table that shows reads 0. A table whose counts disagree is hidden.
- **The total is public.** It always shows, and every other count is hidden against a reader who knows it.
- **`access` is a required function.** No default, and no fallback to the users collection's `access.admin`. The plugin refuses to start without it, or with anything that is not a function. Only an exact `true` allows.
- **Relationship fields need an opt-in.** A relationship is counted only when its collection is listed in `categories`. Auth collections are refused even when listed.
- **Fields the site keeps from readers are refused** at start-up: a counted field, a band field, any field on the path to one, and the title field of a `categories` collection, when it has its own read access, a truthy `hidden`, an `afterRead` hook, or a `virtual` path that reads through a relationship.
- **Collection-level read hooks need an opt-in.** A users collection or a band collection with an `afterRead` or `beforeRead` hook is refused unless its slug is in `allowCollectionReadHooks`.
- **The checks run again when Payload has started**, against the final config, so a plugin listed later cannot undo them. When they pass, the endpoint, the view and the card work from what that second check resolved. If they fail, the start-up log says why, the endpoint answers 503 to someone it would have let in, and nothing is counted. A field with no `label` option is now headed by the label Payload gives it (`kind` reads "Kind"). Titles come from the final config too, so an upload collection with no `useAsTitle` is titled by its file names (Payload makes `filename` its title).
- **One band per field.** Two bands on the same collection and field are refused at start-up, because one less the other shows a group neither protects.
- **Known limits, in the README.** A many-value field shows how many users hold two of its values at once (accepted by the owner). The total is the whole users collection, counted past access control. Collection-level read access on category and band collections is not applied. Two tables side by side can narrow a group that spans both. The counts are not one snapshot.
- **A dashboard card, an admin view and `GET /api/stats`**, read-only.
- **CI and releases.** Typecheck, tests against a MongoDB service container, and build, on Node 22. A `v*` tag stages the package on npm for the owner's approval (RELEASING.md).
- **Test database clean-up.** The throwaway MongoDB container is removed however a run ends, including a Ctrl-C while it is still starting, and a failed start never removes a container the run didn't create.

Tested: 175 tests against a real Payload 3.92.1 and a real MongoDB 8 in a throwaway container. Counts for every table on made-up data (40 accounts), including an account with two roles counted in both, the same value in two array rows counted once, deleted owners left out of bands, and UTC day edges. Hiding: each rule on its own and the expected hidden tables on the made-up site. The two readers below work from made-up kinds of user and the published page, and read nothing of how the plugin lays a report out. A reader who knows the code: for eight report shapes, every possible site up to 9 to 24 users, at minimums 2, 3 and 5, grouped by the page each publishes, with no page ruling out a size from 1 to minimum - 1 for a protected group beyond what the public total rules out. The protected groups are every group a reader could name from one table (for a many-value field: each row, each roll-up, any, none, and the users with some value who lack one). That check fails for four other engines (small counts hidden alone, a neighbor picked by size, "fewer than" labels kept inside hidden tables, blocks left un-nested), for two bands on one field, and, checked by hand, with either kind of many-value remainder taken out of the layout. A brute-force reader that only does arithmetic, on 4,000 random larger sites at minimums 3 and 5, with the total known. Three tests pin the accepted limits: a many-value field gives away the overlap and what follows from it, with no other group of a two-value field narrowed, and a group spanning two fields can be narrowed. The second start-up check, on a real second Payload where a later plugin hides a counted field: the log says why, the endpoint answers 503 and no count is made. A real third Payload where a later plugin puts read access on a category title field and makes another field the title: the rows carry the new titles and the old ones appear nowhere. Refusals at the endpoint, the card and the view for logged-out requests, a user with no role, three other roles, a user who may open the admin panel and an admin-flagged user from another auth collection; custom access answers other than `true`; 52 start-up refusals for bad options, plus a missing `access` and eight values of `access` that are not functions. No name, email or ID in the JSON, the card or the view. Removal of the test database container on SIGINT, SIGTERM and SIGHUP, with a stand-in process in the suite and with real SIGINT and SIGTERM by hand. Start-up of that container with a stand-in docker: removal set up before the first start, a taken port retried up to five times, any other error thrown at once, and a container that already had the name never removed.
Not tested: the card and the view in a browser inside a running Payload admin (they are rendered to HTML in tests, and the view's page frame from `@payloadcms/next` is typechecked only); the import map step; Postgres and SQLite; Node 22 locally (CI runs it); a site with real data; the start-up refusals for virtual fields, afterRead hooks, collection-level read hooks and duplicate bands against a booted Payload (they are tested on the options resolver with plain config objects; only the hidden-field case runs on a real one); a later plugin adding a read hook, against a real Payload (tested with a stand-in); what a many-value field with three values and a roll-up gives away beyond the overlap, which is stated as bounds and not measured; the readers on shapes larger than those eight, such as a field with more than four values, three roll-ups, or every table at once; a write landing between two counts of one report; a reader who compares reports saved at different times. The last two are stated as limits in the README.
